# Codex Candy Eval 独立功能模块迁移方案

更新日期：2026-11-13。状态：源码迁移与模块化已在长期分支 `custom` 实施；本文记录实施结果、验证状态和后续维护方式。尚未推送到自有仓库，也未进行真实账户烟测、部署或发布。

上游升级、自定义开发、定制发布和回退步骤见[维护手册](codex-candy-eval-maintenance.md)。

## 1. 已确定的实施路线

已在 Sub2API v0.2.21 基线上迁入 Codex Candy Eval，并整理为独立功能模块。保留现有评估功能、界面和历史格式，通过明确接口连接宿主账户服务、路由和启停流程。后续在普通 Go/JS 源码上定制，长期维护定制分支。

本次包含：源码与测试导入、恢复测试确定性修复、模块生命周期与状态管理、账户适配和存储边界整理、构建验证及升级/回退说明。通用插件平台、`.s2plugin` 改造、完整 Vue 界面重写、数据库历史迁移及分布式调度不纳入本次范围。模块化可以减少升级冲突，但不能消除宿主接口变化带来的兼容工作。

这与项目本身的实现方式一致：作者称其为插件，但交付的是“上游源码 + 有序补丁 → 完整 Sub2API 二进制 + 安装器”，并非运行时加载的独立插件。

## 3. 作者如何开发“插件”

### 3.1 代码与构建组织

| 部分 | 实际职责 |
| --- | --- |
| `patches/0001-evaluation-core.patch` | 评估核心、运行任务、历史、基础页面资源 |
| `0002-evaluation-data.patch` | 指纹参考库等数据 |
| `0003-vendor-assets.patch` | Markdown、数学排版等前端第三方资源 |
| `0004-admin-channel.patch` | 管理接口、账号请求适配及传输错误标记 |
| `0005-inspection.patch` | 定时巡检、设置、模型控制和通知 |
| `0006-evaluation-ui.patch` | 独立评估页面资源及 Vue iframe 容器 |
| `0007-sub2api-integration.patch` | 启停、路由、菜单、国际化、字段保留等宿主接线 |
| `tests/` | Go 核心/适配层测试、JS DOM 测试、构建和安装器测试 |
| `scripts/build.py` | 拉取固定 tag、应用补丁、构建前端、测试、编译嵌入前端的服务器、打包安装器 |

构建器支持两种组织：当前仓库自己的 `patches/`，或组合仓库中 `plugins/` 下的 Git 子模块。按照插件路径和补丁文件名排序应用；没有通用扩展点自动解决多个补丁修改同一处代码的问题。

Go 测试通过 `// sub2api-package: ...` 指定目标包，构建器临时复制测试到打补丁后的源码包内执行；JS 测试从目标前端依赖中加载 jsdom。测试不是只在补丁仓库原地执行就能全部运行。

`UPSTREAM_TAG` 未指定时构建器查询 GitHub 最新 release；CI 手工输入默认值目前仍为 v0.2.20。我们的迁移必须显式固定 v0.2.21 与来源 commit，避免隐式跟随版本漂移。作者还固定了 pnpm 12.16.1 并生成 workspace 配置；不应未经验证就替换我们现有依赖管理流程。

### 3.2 运行架构

```text
/admin/codex-eval（Vue 管理页）
  → 同源 iframe /codex-eval（Go embed 的 HTML/CSS/JS）
  → /api/v1/admin/codex-eval/*（管理认证、审计等中间件）
  → internal/codexeval（任务、评分、指纹、历史、巡检）
  → Sender / Resolver 回调
  → AccountTestService（账户凭证、各供应商协议、代理与 HTTP 请求）
  → 模型供应商
```

核心通过 `Sender` / `Resolver` 回调与宿主连接；凭证保留在账户服务层。新增适配器实现多供应商请求/流式响应转换，不是简单调用一遍公开网关，因此必须单独验证与宿主网关传输、代理、限制和错误语义的关系。

UI 直接读取同源 `localStorage.auth_token`，不是官方插件 UI Bridge。外层 iframe 没有 sandbox；模型生成的鹈鹕内容则放入 `sandbox="allow-scripts"` 的内层 iframe。静态页面路由公开，数据和操作走管理 API；不能把静态页面可访问误判为管理数据公开。

### 3.3 状态与生命周期

- 活动任务、取消句柄、巡检状态在进程内；停止服务时调用 `StopInspection()`。
- 历史写入 `cfg.Pricing.DataDir/codex-eval/history.json`，按账户、测试类型保留最近 20 条，临时文件加重命名落盘；兼容旧格式并备份旧历史。
- 巡检配置通过现有 settings 仓储保存，键前缀为 `codex_eval_inspection_`。
- 账户扩展字段记录巡检开关、判定、已移除模型；巡检可修改账户优先级与模型映射。
- 没有新增 SQL migration；这不代表没有持久化副作用。
- 通知支持 ntfy/Bark。配置服务将相关值交给现有 settings 仓储；迁移时需核查通知秘密的实际落盘保护与脱敏，不假定等同于官方插件的整体加密配置。

## 4. 与宿主现有插件机制的差异

依据当前 `backend/pkg/pluginapi/README.md` 与 `v1/plugin.proto`：

| 维度 | Candy Eval 补丁模式 | 宿主 `.s2plugin` |
| --- | --- | --- |
| 交付 | 整套重编译服务器 | 签名 ZIP、独立运行时与静态 UI |
| 执行 | 宿主进程内 | 子进程、本机 gRPC |
| UI | 同源页面，读取管理员 Token | sandbox iframe、受控 UI Bridge |
| 能力 | 直接接入宿主内部服务 | 当前仅接受 OpenAI OAuth outbound transport 能力 |
| 账户操作 | 跨供应商评估、更新模型和优先级 | HostService 有 KV、ListAccounts、ResolveOutboundIdentity；缺少评估任务与账户写回契约 |
| 更新 | 编译发布整个宿主 | 管理页安装/启停兼容包 |

现有 HostService 已有账户读取与身份解析，并非毫无复用基础；但范围受插件能力限制，没有完整的多供应商评估和写回接口。直接改成 `.s2plugin` 至少需要新增能力声明、宿主授权、任务 API、UI 操作 Bridge、账户变更接口与测试，会把本次迁移扩大为插件平台开发。

## 5. 实施结果与交付边界

### 阶段 A：保真迁入（已完成）

1. 已从 v0.2.21 建立长期自定义分支 `custom`，作为本次迁移及后续定制功能的主线；宿主 SHA、来源 SHA 和来源许可证均有记录。
2. 已按顺序迁入 7 个补丁包含的核心、适配层、UI 和相关测试。Go/JS 测试与 fixtures 已进入仓库；指纹恢复 fixture 使用确定性抽样，避免随机导致的偶发失败。
3. 已保存来源 LICENSE 和第三方 notices，并引用来源 commit；正式分发仍需按实际许可证保留声明及相应源码义务。
4. 沿用现有构建与部署流程，产物为包含评估功能的完整服务器或镜像；不使用外部安装器覆盖服务。
5. 自动巡检保持原有设置行为。部署前需确认开关状态，并先验证手动评估、取消与历史；账户自动调整带来的副作用见第 6 节。

### 阶段 B：小范围模块化（已完成）

保留 `internal/codexeval` 核心目录和现有 Sender/Resolver 能力，不改变评估算法与产品交互。当前实现结构如下：

| 模块边界 | 已实施内容 |
| --- | --- |
| 模块生命周期 | 创建独立服务实例，由宿主装配依赖；集中初始化、启动、停止和任务清理。路由注册不再承担启动巡检的职责。 |
| 状态管理 | 将任务、取消句柄、巡检和历史相关可变全局状态收敛到实例，明确锁和所有权；保留不可变题库和静态资源。 |
| 账户适配 | 薄适配层复用宿主账户、模型目录、代理和请求服务；保留已有回调或按需要组合为接口，不让评估核心依赖宿主具体服务类型。 |
| 历史存储 | 提取最小 `HistoryStore` 边界，本次仍使用兼容现有路径与格式的 JSON 实现。 |
| 巡检写回 | 将评估判定与账户变更执行分开，通过明确的回调/接口完成模型、优先级和扩展字段写回，保留原有行为。 |
| 路由与 UI | 集中评估路由注册，复用管理认证及资源权限；保留现有 Vue iframe 入口和页面资源。 |

宿主保留四类接入点：模块依赖装配、路由注册、启停接线、前端入口。账户字段防覆盖及通用 HTTP 错误语义等必要宿主改动单独记录，不能为了形式上的隔离而删除或隐藏。

目标依赖方向：

```text
宿主装配与启停 → 评估模块实例 → 评估与巡检核心
管理接口      → 评估模块实例 → 历史存储接口 → JSON
评估与巡检核心 → 账户调用/写回接口 → 宿主适配层 → 账户服务
```

保持原有调度行为，不重写调度算法。先定位并修复指纹恢复测试问题，再进行模块化并执行同一套回归，区分来源问题与重构引入的问题。导入、修复、模块化分别提交。

后续有实际需求时再扩展 `Evaluator`（新测试类型）、`Notifier`（新通知渠道）、数据库存储或原生 Vue 页面；不预先搭建通用注册框架。

### 阶段 C：验证与发布（源码验证完成，外部验收未开始）

初始恢复测试失败来自随机抽样造成的非确定性 fixture；已改用固定挑战样本并加入回归。源码验证使用仓库工具链 Go 1.27.3；此前 Go 1.27.1 隔离测试只作为发现线索。

- 核心：四种测试、重试、超时、取消、历史上限、旧格式恢复。
- 模块化：实例间状态隔离、重复启停的预期行为、取消和退出清理、JSON 存储替换边界；模块化前后功能和历史兼容性一致。
- 适配：OAuth/API Key/上游类型、各供应商协议与流式解析、代理、模型目录、传输异常。
- 权限：新增接口继承管理认证、审计及受限密钥权限策略；路由测试覆盖匿名/普通用户拒绝和受限密钥拒绝。清空历史、修改巡检配置接入二次验证，UI 通过同源 iframe 消息请求宿主验证。
- 巡检：手动评估不改账户；自动巡检降级/恢复时模型和优先级变更正确；账户编辑不会覆盖巡检受管字段；退出时任务正确停止。
- 前端：类型检查、国际化检查、构建和 DOM 测试；登录过期、主题切换、错误展示、生成内容隔离。
- 宿主回归：补丁修改了通用 HTTP 错误包装，应验证正常网关、错误判断和重试没有回归。
- 发布：测试环境单实例启用，以少量明确选定账户验证真实请求和额度消耗，再切换正式环境。

## 6. 必须处理的迁移边界

1. **部署范围**：本次验收限定单实例并持久挂载历史目录。进程内手动任务、历史和自动巡检都缺少集群协调，不能仅关闭自动巡检就声称支持多副本。生产拓扑尚未确认，部署前必须核实；多副本部署暂不启用该功能，另行设计唯一执行实例及请求路由，或共享存储与任务协调，不在本次迁移中隐式扩大范围。
2. **授权**：新增批量接口接收账户 ID，不应只检查“能访问管理页”。当前受限账户中间件主要匹配 `/admin/accounts`，新 `/admin/codex-eval` 路径需结合管理认证的策略判断单独核验；不能仅凭已有中间件就声称资源隔离完成，也不能据此直接断言存在绕过漏洞。
3. **账户副作用**：巡检会修改模型映射、优先级及 Extra。上线前保存这些字段的快照，处理并发编辑与恢复策略；仅回滚程序不会自动恢复已改账户数据。
4. **历史和回退**：备份数据目录中的 codex-eval 以及巡检 settings；旧格式备份不包含升级后的新记录。回退先停巡检，恢复原程序，再按需要恢复数据与账户变更。
5. **可维护性**：自定义代码在展开的源码上开发，不手改大段 patch 文本。导入、兼容修复、自定义能力分成不同提交；每次升级宿主 tag 都执行合并/补丁预检和功能回归。

## 7. 后续开发、上游更新与交付

### 7.1 分支与提交组织

长期主线为 `custom`，从 v0.2.21 建立。本次迁移已直接在此分支承载，后续插件改进、自定义业务功能、兼容修复和上游版本更新最终都汇入该分支；不再先建立迁移临时分支、迁移后另选主线。

- `main`：保留上游原版基线，不提交自定义业务代码；其更新不自动替代定制版本。
- `custom`：本地长期定制开发与交付主线，不按插件或上游版本重新创建，不通过 reset 到上游 tag 的方式升级。当前尚未推送到自有远程。
- 可选验证分支：较大改动或上游升级需要隔离验证时，从 `custom` 创建短期分支；通过验证后合回 `custom`，它们不承担长期交付职责。日常定制可直接在长期主线上推进。
- 发布 tag：从已验证的 `custom` 提交创建独立命名的定制 tag，例如 `custom-v0.2.21.1`，对应固定镜像/二进制。部署引用已验证的发布版本，而不是自动跟随分支最新提交。

当前 `origin` 指向公共上游 `Wei-Shaw/sub2api`，本次没有推送。配置自有 fork/仓库作为定制分支推送目标，并保留公共上游拉取入口后，令 `custom` 跟踪自有仓库同名分支，不跟踪公共上游 `main`。自有远程仓库地址尚未确定；这不阻塞本地源码迁移，但远程备份、CI 和发布依赖该配置。

长期分支通过 merge 保留上游与自定义历史；已共享的主线不做 rebase 或强推改写。

提交分为：来源功能导入、兼容/缺陷修复、模块化整理、后续自定义能力。维护来源记录及宿主接入点清单，记录每处必要宿主修改的原因和对应测试。

### 7.2 Sub2API 发布新 tag 时

1. 拉取 tag，记录待升级 SHA 和 `custom` 的升级前提交；需要隔离验证时，从该提交创建 `upgrade/sub2api-<version>`。
2. 将选定上游 tag 合并到验证分支（未使用验证分支时合入 `custom`），保留已有模块和自定义提交；首次导入后不重复应用原始整套补丁。
3. 处理源码冲突，重点检查账户适配、权限、HTTP 错误语义、生命周期、路由和前端入口。即使没有文本冲突，也需检查行为兼容。
4. 使用目标版本要求的工具链，执行宿主构建、插件测试和必要回归；CI 不通过不发布。
5. 测试环境验证后，将验证分支合回 `custom`（若使用）；如主线期间有其他变更，对合并结果重新验证。随后从长期主线创建定制发布 tag，发布自己的完整镜像/二进制。官方原版产物不包含该模块，不能直接替换定制产物而保留功能。
6. 保存上一版定制产物及数据备份；回退同时考虑程序、历史格式和账户写回数据。

### 7.3 Candy Eval 来源项目更新时

与宿主升级分开处理：对比已记录来源 SHA 与新 SHA，将新增功能或修复适配到模块源码，更新来源记录、声明和测试。来源项目仍以补丁发布时，可在临时目录展开两个版本后比较源码差异；不直接用新补丁覆盖我们已经模块化或定制的代码。

每个发布版本同时记录宿主 tag/SHA、插件来源 SHA、自定义 revision。当前不建立额外的补丁组合仓库；只有确需多个插件或多个宿主版本的组合交付时再评估。

### 7.4 CI 与版本发布适配
